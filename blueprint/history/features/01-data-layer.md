# Feature: Data layer

**From build-plan:** feature 1
**Status:** verified

## Goal

Stand up the local SQLite data layer (Drizzle ORM + better-sqlite3) that every
later feature reads and writes: `Anime`, `Artist`, `Song`, `Card`, and
`ReviewLog` tables, with migrations that apply automatically when the app
boots. This is pure foundation - no UI, no API routes - but it locks the exact
schema contract the rest of the app depends on, including the SQLite file
location left as a TODO in `project-overview.md`.

## In scope

- Drizzle ORM + better-sqlite3 installed and configured in `nuxt-app/`
- Schema definitions and generated migrations for `Anime`, `Artist`, `Song`,
  `Card`, `ReviewLog`
- A server-side DB client singleton, and migrations applied automatically on
  server boot (no manual migrate step for local dev)
- A dev seed/smoke script proving the schema round-trips correctly across all
  five tables and their relationships
- Locking the exact column set, types, and constraints as the load-bearing
  contract every later feature builds on
- Deciding the SQLite file's on-disk location (open TODO from the overview)

## Out of scope

- `MediaLibrarySettings` table (feature 2 - Media library settings)
- Any UI, server API routes, or CRUD endpoints (features 3/4 build those)
- AniList/animethemes.moe API clients (feature 3)
- The Leitner-box scheduling algorithm itself (feature 6 implements it; this
  feature only stores the `box` / `nextReviewAt` fields it needs)
- Seeding real production data - the seed script is a throwaway dev smoke
  check, not a data-import pipeline

## Build loop

Build one step at a time, never the whole feature at once.

1. Plan mode lays out the step before any code.
2. The AI implements just that step.
3. It shows the diff (not full files); you read it and understand it.
4. You approve, then choose whether to commit a checkpoint or roll straight on.
   Checkpoints are optional; `/complete` makes the real feature-level commit at the end.

Never accept a step you haven't read. If a diff is too big to review, the step was too big, so split it.

## Data / contracts

Load-bearing: every later feature reads or writes exactly these shapes.
Column names are `snake_case` in SQLite; TS object keys are `camelCase`
(Drizzle maps between them).

**Anime**
- `id` integer PK autoincrement
- `ani_list_id` integer NOT NULL, UNIQUE - external AniList reference
- `animethemes_id` integer NULL - external animethemes.moe reference
- `title_english` text NOT NULL
- `title_romaji` text NOT NULL
- `title_native` text NOT NULL - Japanese

**Artist**
- `id` integer PK autoincrement
- `name` text NOT NULL

**Song** (a specific OP/ED theme track)
- `id` integer PK autoincrement
- `anime_id` integer NOT NULL, FK -> `anime.id`
- `artist_id` integer NOT NULL, FK -> `artist.id`
- `title` text NOT NULL - as sourced from animethemes.moe/AniList
- `theme_slot` text NOT NULL - e.g. `"OP1"`, `"ED2"`
- `animethemes_theme_id` integer NULL - external reference, used to re-fetch
  or re-link media later
- UNIQUE (`anime_id`, `theme_slot`) - one row per theme slot per anime

**Card**
- `id` integer PK autoincrement
- `song_id` integer NOT NULL, FK -> `song.id`
- `local_video_path` text NULL - within the configured media library
- `local_audio_path` text NULL
- `animethemes_video_url` text NULL
- `animethemes_audio_url` text NULL
- `box` integer NOT NULL, default `1` - current Leitner box
- `next_review_at` integer (unix timestamp) NOT NULL, default now - a new
  card is due immediately
- `created_at` integer (unix timestamp) NOT NULL, default now
- Quiz type (video vs audio-only) stays **derived**, not a stored column -
  video if any video source is present, audio-only otherwise

**ReviewLog**
- `id` integer PK autoincrement
- `card_id` integer NOT NULL, FK -> `card.id`, **ON DELETE CASCADE** (deleting
  a card cleans up its review history)
- `reviewed_at` integer (unix timestamp) NOT NULL, default now
- `result` text NOT NULL - `'pass'` or `'fail'`, enforced primarily via a
  TypeScript union type (`.$type<'pass' | 'fail'>()`); add a DB-level CHECK
  constraint too only if the installed `drizzle-orm` version's sqlite-core
  supports declaring one cleanly, don't fight the API to force it
- `box_before` integer NOT NULL
- `box_after` integer NOT NULL

No `Deck` table and no `MediaLibrarySettings` table in this feature - see
Out of scope.

**DB file location (resolves the overview's open TODO):**
`nuxt-app/.data/gaq-srs.db`. Already covered by `nuxt-app/.gitignore`'s
`.data` entry, so the database file is never committed.

**FK delete behavior:** only `ReviewLog -> Card` cascades. The other FKs use
Drizzle's default (no cascade) because no feature in this spec deletes an
`Anime`, `Artist`, or `Song` - that only becomes a real decision once a
feature actually does, and can be revisited then.

## Notes for the AI

- Everything here is server-only (`nuxt-app/server/`) - never import
  `schema.ts` or `client.ts` from `app/` client code, per
  `coding-standards.md`'s server-routes-only rule for DB/filesystem access.
- Use `drizzle-kit generate` + `drizzle-kit migrate`, not `drizzle-kit push` -
  `coding-standards.md` requires real migration files, not direct schema
  pushes.
- If the boot-time migration fails, let it throw and crash the server start;
  don't swallow the error into a warning log. A local single-user app should
  never run against a half-migrated schema.
- better-sqlite3 is synchronous and single-connection, which is fine here -
  there is exactly one user and one process (see project-plan.md Non-Goals).
  Don't add connection pooling.

## Implementation notes

- `better-sqlite3` crashes Bun's own JS runtime (native N-API panic) when a
  script is executed via `bun run <file>.ts` directly - a Bun compatibility
  gap, unrelated to this code. `nuxt dev`/`build`/`preview` are unaffected
  since Nitro doesn't execute server code that way. Worked around by running
  `db:seed` via `node` instead, which required explicit `.ts` extensions on
  relative imports in `server/db/client.ts`, `server/db/seed.ts`, and
  `server/plugins/db.ts` (Node's ESM resolver needs them; Vite/Nitro's
  bundler accepts them too, so this doesn't affect the built app).
